# 03 · 结构化工作集与防丢信息架构

> 本文档回答核心质疑：**“既然任何有损筛选在信息论上都必然丢信息，如何保证 `gp` 在按权重裁剪上下文时依然不丢关键信息？”**  
> 答案不是把全部历史硬塞进单次 Prompt，而是建立 **“外置无损仓库 + 结构化约束账本 + 加权工作集 + 可逆溯源取回”** 四位一体架构。

---

## 1. 核心认知转换：Working Set ≠ Warehouse

| 层级 | 在 `gp` 中的存储载体 | 生命周期与可变性 | 职责边界 |
| :--- | :--- | :--- | :--- |
| **L0：无损外置仓库 (Warehouse)** | `SessionTree` + SQLite `entries` 表（`~/.gp/gp.db`） | **永久不可变（Append-Only）** | 保存 100% 原始消息、工具参数、工具完整输出与思考签名 |
| **L1：结构化低频基底 (Constraint Ledger)** | SQLite `documents` 表（`doc_key = "context_ledger"`） | 仅在约束新增/推翻/完成时**增量结构化更新** | 保存项目目标、硬性约束、已确认架构决策、未决问题；**不存长段叙述** |
| **L2：加权动态工作集 (Weighted Working Set)** | 运行时在内存中由 `PPR + ACT-R + Budgeted MMR/DPP` 组装 | 每轮或按查询意图在 Token 预算 $B_{\text{recall}}$ 内动态筛选 | 专门负责捞回“表面无关但多跳关联”的早期上下文与工具结论 |
| **L3：高频原始局部窗口 (Recent Verbatim Window)** | 当前 Epoch 内未折叠的近期消息 | Epoch 内 **Append-Only**（保 Prompt Caching） | 完整保留指代关系（“它”“刚才那个文件”）、当前工具调用链与近期推理细节 |

## 2. 为什么必须用“结构化约束账本”替代自然语言摘要？

目前 `gp` 的 [`callLLMSummary`](https://github.com/npc1607/gp/blob/main/internal/core/compaction/compactor.go) 会生成一段类似如下的自由文本：
> *"1. Goal & Constraints: 用户一开始希望用 MySQL，后来又讨论了 PostgreSQL 的 JSONB 查询，同时需要注意部署环境隔离……"*

这种做法有 **3 个致命缺陷**：
1. **摘要漂移（Summary Drift）**：第 1 次压缩把 `v1` 写成 `v2`，第 2 次在摘要之上再压缩时，错误被永久固化且无法自检；
2. **状态冲突无法仲裁**：当第 10 轮决定“用 MySQL”，第 55 轮改成“彻底放弃 MySQL 全量切 PostgreSQL”，自由文本往往把两者并列写进摘要，造成模型后续写 SQL 时精神分裂；
3. **无指针无法回溯**：当模型怀疑某条结论记错了时，摘要里没有记录它源自哪条 `entry_id`，不知道该去哪里核实。

### 结构化约束账本（`ContextLedger`）Schema 设计

```json
{
  "version": 12,
  "active_goal": {
    "summary": "为 gp 构建缓存友好且能多跳召回的上下文选择引擎",
    "provenance": ["entry_101"]
  },
  "constraints": [
    {
      "id": "cst_db_01",
      "category": "tech_stack",
      "statement": "后端数据库使用 MySQL 8.0",
      "status": "superseded",
      "superseded_by": "cst_db_02",
      "provenance": ["entry_108"],
      "turn": 10
    },
    {
      "id": "cst_db_02",
      "category": "tech_stack",
      "statement": "全量迁移至 PostgreSQL 16，不再兼容 MySQL 语法",
      "status": "active",
      "supersedes": ["cst_db_01"],
      "provenance": ["entry_245"],
      "turn": 55
    },
    {
      "id": "cst_env_01",
      "category": "environment",
      "statement": "构建机器处于内网隔离环境，禁止执行外网 curl / pip install",
      "status": "active",
      "provenance": ["entry_042"],
      "turn": 4
    }
  ],
  "key_artifacts": [
    {
      "path": "internal/agent/loop.go",
      "role": "Agent ReAct 主循环入口",
      "last_touched_turn": 88,
      "provenance": ["entry_310", "entry_312"]
    }
  ],
  "open_issues": [
    {
      "id": "iss_03",
      "description": "scripts/build_image.sh 构建报 403",
      "status": "open",
      "provenance": ["entry_340"]
    }
  ]
}
```

### 关键工程约束
1. **默认只注入 `status == "active"` 的约束**（可附带极简 `supersedes` 变更脚注防止回滚误判），彻底消除陈旧设定污染。
2. **Canonical 确定性序列化**：注入 Prompt 前按 `id` 字典序规范化输出，**只有账本确实发生字段变更时才更新前缀文本**，平时字节级完全一致，保证 Prompt Caching 最高命中率。
3. **达到最小缓存阈值考量**：主流 API（如 Anthropic / OpenAI）要求前缀达到 `1024` 或 `2048` tokens 才激活缓存；因此 `System Prompt + Tools Schema + ContextLedger` 应当合并作为稳定前缀底座，确保稳稳跨过最小可缓存长度门槛。

## 3. “绝对不丢信息”的闭环保障：双向可逆溯源协议

当某条历史被工作集裁掉（或某条长输出被掩码）时，系统必须保留**轻量索引存根（Stub）**，并在需要时由模型主动调用只读工具无损取回：

| 场景 | 在上下文中留下的可逆线索 | 模型主动取回工具 | 回溯数据源 |
| :--- | :--- | :--- | :--- |
| **历史大段工具输出被折叠** | `gp` 现有 `[已折叠历史工具输出: tool=... call_id=... \| 原文 N 行]` | `restore_observation(call_id, start_line, end_line)`（已实现） | `SessionTree` 中的原始 `RoleTool` |
| **约束冲突 / 需要核实原始措辞** | 账本条目附带 `provenance: ["entry_245"]` | `recall_entries(entry_ids)`（实验新增只读工具） | `gp.db` `entries` 表 |
| **模型意识到工作集可能漏掉某关键词** | 工作集底部附带极简“未展开历史话题/文件索引目录（TOC）” | `search_session_history(query, limit)`（实验新增只读工具） | 基于 `SessionTree` 的内存 BM25 + 图索引 |

> **关键设计原则**：  
> - **90% 的常规情况**：靠 `ContextLedger + PPR/ACT-R/MMR 工作集` **自动一次送准**，不增加多余工具往返轮次；  
> - **10% 的边界/歧义/长输出回查**：靠 `provenance` 指针与 `restore_observation` / `recall_entries` **100% 无损兜底**。
