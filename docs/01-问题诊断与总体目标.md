# 01 · 问题诊断与总体目标

> **目标 Agent**：[`gp`](https://github.com/npc1607/gp)（Go Coding Agent Harness）  
> **核心命题**：如何在严格控制 Token 预算并最大化命中 Prompt Caching 的前提下，让 `gp` 在百轮级长任务中**不丢失关键约束**，且能**发现表面看似无关（A 与 B 无字面交集）的隐性关联**。

---

## 1. `gp` 现有上下文机制诊断（源码基线）

截至目前，`gp` 的 `runReActLoop`（[`internal/agent/loop.go`](https://github.com/npc1607/gp/blob/main/internal/agent/loop.go)）每次请求大模型前执行如下链路：

```text
SessionTree.GetLinearContext()
  ──▶ applyObservationMasking(messages, window=5)   // 保留最近 5 轮工具原文，更早大输出 (>400B 或 >8行) 折叠为占位符
  ──▶ maybeAutoCompact(ctx, masked)                 // 估算 token >= 0.80 * contextWindow 时触发两级压缩
  ──▶ Provider.StreamChat(ctx, req)                 // 发送组装后的全量 messages[]
```

这套机制（详见 [`Observation-Masking与DTOC上下文防污染方案.md`](https://github.com/npc1607/gp/blob/main/docs/Observation-Masking与DTOC上下文防污染方案.md)）已经做对了三件事：
1. **存储与视图分离**：[`SessionTree`](https://github.com/npc1607/gp/blob/main/internal/core/session/session.go) 与 [`SqliteStorage`](https://github.com/npc1607/gp/blob/main/internal/core/storage/sqlite/sqlite.go) 永久保留无损历史 `entries` 与 `documents` 表；
2. **低成本消除工具输出膨胀**：最近 5 轮以外的大段 `bash`/`read`/`grep` 输出会被 0ms 折叠，并通过只读工具 [`restore_observation`](https://github.com/npc1607/gp/blob/main/internal/agent/observation.go) 按 `call_id` 精确分页取回；
3. **统一追踪缓存指标**：[`ai.TokenUsage`](https://github.com/npc1607/gp/blob/main/internal/ai/types.go) 已记录 `InputTokens`、`OutputTokens`、`CacheReadTokens`、`CacheWriteTokens`。

但在真实长程任务中，现有链路仍暴露出 **4 个结构性瓶颈**：

| 序号 | 现状瓶颈 | 具体表现与源码根源 | 后果 |
| :--- | :--- | :--- | :--- |
| **G1** | **压缩前线性全量发送** | 在触达 `0.80 * contextWindow`（如 1M 模型要到 800k，200k 模型要到 160k）之前，所有用户/助手文本、推理过程、小工具输出都会全量反复重发 | 中长会话输入 token 持续膨胀，注意力和推理信噪比下降 |
| **G2** | **无隐性/多跳关联召回** | 历史消息被压缩后只剩静态摘要，无图结构或加权检索；若第 5 轮的业务/架构限制 A 与第 90 轮任务 B 无共同关键词，模型看不到 A | 遗忘早期硬限制、违背前置条件、重复踩坑 |
| **G3** | **纯自然语言摘要漂移** | [`callLLMSummary`](https://github.com/npc1607/gp/blob/main/internal/core/compaction/compactor.go) 把早期历史压成 5 段自由文本，无结构化约束 Schema，也无原始 `entry_id` 指针 | 新旧决策冲突时无法仲裁（例如早期用 MySQL、中期切 PostgreSQL，摘要可能混写或丢失切换关系） |
| **G4** | **滑动窗口破坏前缀缓存** | `applyObservationMasking(..., 5)` 每完成一轮工具调用就把 `cutoffIdx` 后移 1 轮，修改了原本处于前缀中的历史 `RoleTool` 内容；[`anthropic.go`](https://github.com/npc1607/gp/blob/main/internal/ai/providers/anthropic/anthropic.go) 也未设置 `cache_control` 断点 | 历史前缀哈希每轮失效，KV / Prefix Cache 频繁重算，真实 API 账单居高不下 |

## 2. 理论纠偏与设计共识

在方案讨论阶段，我们对早期直觉方案进行了严格审视，以下 **5 项纠偏**将作为本实验项目的硬性设计准则：

1. **禁用裸 Surprisal（$-\log P$）作为独立权重**
   - **错误原因**：信息熵高只说明“模型没料到”，不等于“对任务有价值”。UUID、哈希、URL、编译报错十六进制地址、乱码全是超高 $-\log P$，直接按熵加权会把噪音顶到最前面；且若用下游同源模型打分还会引入“自恋偏差”。
   - **修正**：采用 **任务条件信息增益 / BM25 精确标识符匹配 + 跨信号融合（RRF）**，信息密度只能做惩罚项（过滤客套/复读），不能脱离相关性单独拉高权重。

2. **用 ACT-R 幂律遗忘替代错误的 Hawkes $\gamma$ 改造**
   - **错误原因**：标准 Hawkes 过程的衰减率 $\gamma$ 是全局常数，声称“每次提及既叠加脉冲又减缓自身 $\gamma$”在数学上自相矛盾；且固定指数衰减叠加脉冲本质就是一阶 IIR 低通滤波。
   - **修正**：采用认知记忆中更符合“越常被验证/提及越难遗忘”的 **ACT-R 幂律激活（Power-Law Forgetting）**，并在消融实验中与 per-item 指数半衰期做对比。

3. **抛弃卡尔曼滤波线性类比，改用“结构化工作集 + 外置无损仓库”**
   - **错误原因**：自然语言摘要是非线性、非高斯、不可加的有损算子，无法推导最优卡尔曼增益 $K$；把“不丢信息”寄托在向单次 Prompt 硬塞内容上在信息论上不可能。
   - **修正**：重新定义职责边界——
     - **Context（工作集 Working Set）**：有界预算、高信噪比、结构化低频约束账本 + 动态按权召回 + 近期原始窗口；
     - **Storage（仓库 Warehouse）**：`gp.db` `entries` 永久无损；
     - **不丢信息 = 任意被移出工作集的细节，均保留 `entry_id` / `call_id` 溯源指针，可被工具按需无损回查**。

4. **结构化低频基底 + Provenance（溯源指针）**
   - 早期硬性约束（目标、环境限制、禁止路径、技术栈选型变更）不再混在自由文本摘要中，而是沉淀为**可 diff、可覆盖（`active` / `superseded`）、每条带 `source_entry_id` 的结构化 JSON 约束账本**。

5. **Prompt Caching 前缀稳定性是一等公民约束**
   - Token 少 $\neq$ 账单低。在计费模型中，缓存命中单价通常仅为未命中输入的 **10%–50%**（且 Anthropic/OpenAI 有最小可缓存长度门槛，如 1024 / 2048 tokens）。
   - **待实验仲裁的布局分歧**：动态召回块究竟放在高频滑窗**之前**还是**之后**？`Observation Masking` 究竟按轮滑动还是按 **Epoch 块冻结**？不靠猜，直接在实验 `E4` 中用真实含缓存计费公式跑出结论。

## 3. 实验想要达成的 4 个量化目标

所有实验组必须同时接受以下 **4 个维度** 的检验，避免出现“省了 Token 但答错题”或“准确率高但缓存全碎、账单更贵”的局部最优假象：

| 目标维度 | 核心指标 | 计算方式 | 预期达标线（相对于全量基线 B0 与现状基线 B1） |
| :--- | :--- | :--- | :--- |
| **1. 隐性关联准确率** | **Multi-Hop Task Pass@1 & Evidence Recall** | 回答正确率 + 工作集中成功包含跨跳关键前提 `entry_id` 的比例 | 多跳关联召回率较纯向量 Top-K 提升 **$\ge$ 25%**；最终任务准确率逼近全量基线 `B0`（差距 **$\le$ 3%**） |
| **2. 约束保真与抗污染** | **Constraint Fidelity & Zero-Conflict Rate** | 严格遵守当前有效约束的比例；未误用已作废（`superseded`）历史方案的比例 | 有效约束遵守率 **$\ge$ 95%**；陈旧/已推翻约束误触发率 **$< 5$%**（显著优于纯自然语言摘要） |
| **3. 含缓存真实成本** | **Effective Cost per Turn (USD) & Cache Hit Ratio** | 按真实 API 定价计入 `Uncached Input + CacheWrite + CacheRead + Output` 后的总花费，以及 `CacheRead / TotalInput` | 在 50–150 轮长会话中，真实输入总账单较全量发送 `B0` 降低 **$\ge$ 45%**，且不高于当前 `B1` 的单轮成本 |
| **4. 额外计算延迟** | **Context Build Overhead (p50 / p95 ms)** | 本地建图 + PPR 扩散 + ACT-R + MMR/DPP 子集选择总耗时（不含 LLM 网络请求） | 本地纯 Go 计算延迟 **p95 $\le 30\text{ ms}$**（无本地大模型打分阻塞热路径） |

## 4. 非目标（Scope Guard）

为防止实验失焦，本项目首期**明确不做**：
- 不引入重型外部向量数据库（如 Milvus / Qdrant）或独立图数据库（Neo4j）：`gp` 的定位是单二进制轻量 Agent，所有图与向量索引必须能在内存 + 现有 `SQLite`（`~/.gp/gp.db`）内毫秒级运行。
- 不依赖每次筛选都调用昂贵 LLM 打分：上下文选择器的开销必须远小于省下来的 LLM 成本与延迟。
- 不在实验指标未跑通前修改 `gp` 线上核心 `RunLoop` 逻辑。
