## 1. 大模型的 Prompt Caching，本质上是“最长公共前缀（LCP）缓存”

你可以把每次调 LLM API 想象成**把一个巨大的字符串数组 `messages[]` 发给远端计算节点**。为了节省算力，模型厂商会在服务端缓存请求前缀对应的中间计算结果（KV Cache）。

但它的缓存键（Cache Key）极其苛刻：**必须从第 0 个 Token 开始，逐字节/逐 Token 完全一致（Exact Prefix Match）**，且前缀长度通常要跨过最小门槛（如 `1024` 或 `2048` tokens）才会激活。

计费口径通常如下：

$$
C_{\text{in}}(t) = c_{\text{base}} \cdot T_{\text{uncached}}(t) + c_{\text{read}} \cdot T_{\text{read}}(t) + c_{\text{write}} \cdot T_{\text{write}}(t)
$$

- **命中缓存的部分（`CacheRead`）**：单价通常只有正常输入的 **10%–50%**（例如 $c_{\text{read}} = 0.1 \times c_{\text{base}}$）；
- **一旦第 $k$ 个 Token 发生任何改动（删字、改字、插新内容）**：第 $k$ 个 Token **之后的所有内容缓存全部失效**，全部按原价 $c_{\text{base}}$ 重算（部分厂商如 Anthropic 还会收取 $1.25 \times c_{\text{base}}$ 的 `CacheWrite` 写缓存溢价）。

## 2. 看看 `gp` 现在的滑窗为什么会“缓存全碎”

在 `gp` 现有代码中，每轮请求前都会执行 `applyObservationMasking(messages, window=5)`：只保留最近 5 轮工具的完整输出，第 6 轮及更早的大输出直接替换成 `[已折叠...]` 占位符。

从后台视角看，这相当于**每写一条新日志，就去 `UPDATE` 历史第 $T-5$ 条记录的内容**：

```text
第 10 轮发送: [System] [Turn 1..4 已折叠] [Turn 5 原文] [Turn 6..10 原文]
第 11 轮发送: [System] [Turn 1..4 已折叠] [Turn 5 变成折叠!] [Turn 6..11 原文]
                                            ▲
                                    这里改了，后面 Turn 6..10 的缓存全穿透！
```

结果就是：**虽然历史 Token 少了，但每轮都在修改前缀中间的 `Turn T-5`，导致后面的历史根本吃不到缓存**。

### 后台解法：Epoch 冻结 + 拼接顺序优化（`E4` 实验）

项目提出了两招来解决前缀击穿：

1. **Epoch 批量冻结（类似 LSM-Tree Compaction / WAL 切段）**  
   不再每轮改第 $T-5$ 轮，而是每隔固定步长（例如 `Epoch = 8` 轮）才批量折叠一次。在同一个 Epoch 的 8 轮内，历史前缀**严格 Append-Only（只追加、零修改）**，连续 8 轮吃满前缀缓存。
2. **动态召回放哪里？（`E4-A` vs `E4-B`）**
   - **`E4-A`**：`[固定基底] → [动态召回 S] → [高频滑窗 + Query]`  
     优点是近期滑窗紧贴 Query（符合近因注意力）；缺点是每轮 `S` 变了，后面的滑窗缓存全碎。
   - **`E4-B`**：`[固定基底] → [Epoch 内只增不减的高频滑窗] → [动态召回 S + Query]`  
     优点是从头到高频滑窗结束全静态追加，缓存命中率极高；需要通过实验验证召回块夹在中间是否影响指令遵循精度。

## 3. “绝对不丢信息”的后台架构：WAL + 物化视图 + 外键溯源

很多人一听“裁剪上下文”，第一反应是“那信息不就丢了吗？”。其实后台系统天天都在做这件事——**冷热分离 + 索引回查**。

本项目将上下文拆成了 4 层：

| 层级 | 后台工程类比 | 项目中的载体与职责 |
| :--- | :--- | :--- |
| **L0：Warehouse（无损仓库）** | **Append-Only WAL / MySQL 主表** | `SessionTree` + SQLite `entries` 表，100% 永久保留所有原始消息和工具输出 |
| **L1：Constraint Ledger（结构化账本）** | **状态机物化视图** | 存进 SQLite `documents` 表。用 JSON 记录硬性约束（如“用 MySQL”被第 55 轮推翻为“切 PostgreSQL”，旧记录标 `status: "superseded"`），每条带 `provenance: ["entry_245"]`（**外键指针**） |
| **L2：Weighted Working Set（动态工作集）** | **按需召回的缓存视图** | 每轮在预算内挑出和当前问题最相关的历史片段 |
| **L3：Recent Window（近期窗口）** | **热数据环形缓冲** | 当前 Epoch 内未折叠的近期对话 |

**为什么这样就不会丢信息？**  
因为**工作集（Context）$\neq$ 数据库（Warehouse）**。哪怕某条细节没放进本次 Prompt，只要账本或索引里留了 `entry_id` / `call_id` 指针，模型遇到疑点时可以调用只读工具（`restore_observation`、`recall_entries`、`search_session_history`）像查主键一样无损捞回来。
